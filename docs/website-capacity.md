# 网页版的承载力与稳定性

评估对象：https://munword-formatter.pages.dev/（v1.8.5）。评估日期：2026-10-07。

## 一句话结论

**网页版几乎没有“人太多就挤爆”的问题。** 真正要担心的只有两件事：

- 国内网络能不能顺畅打开 `pages.dev`；
- 用户自己的电脑处理特大文件时会停顿几秒。

## 打个比方：发菜谱，不开饭馆

普通网站像一家饭馆：所有客人的菜都由同一个后厨做，客人一多就排队，厨房一忙就出错。

这个网页版更像**发菜谱**：

1. Cloudflare 只负责把“菜谱”（网页程序，压缩后约 0.27 MB，比一张手机照片还小）递给你；
2. 排版这道菜，是在**你自己的浏览器**这口锅里做的；
3. 原稿从不离开你的电脑，服务器上没有后厨，也没有排队。

所以 1 个人用和 1 万个人同时用，每个人处理文件要等的时间都一样。

## 承载力

### 服务器端：发菜谱的柜台有多宽

| 项目 | 数值 | 说明 |
|---|---|---|
| 每次打开下载多少 | 约 275 KB（gzip 压缩后） | `app.js` 267 KB + 样式 7 KB + 页面 1 KB；共 4 个请求 |
| 再次打开 | 每个文件只确认“有没有更新”，几乎不下载 | 静态站设置为 `Cache-Control: no-cache`，浏览器会重新校验 |
| 处理文件时联网吗 | 不联网 | 识别、排版、预览、模板都在浏览器里完成 |
| Cloudflare 免费版对静态文件的限制 | 请求数、流量都不限、不收费 | [Pages 限制说明](https://developers.cloudflare.com/pages/platform/limits/) |
| Cloudflare 全网带宽 | 超过 500 Tbps，覆盖 330 多个城市 | [Cloudflare 官方博客](https://blog.cloudflare.com/500-tbps-of-capacity/) |

算一笔账：

- 一场 1000 人的会议，所有人在同一分钟打开网页，总共只需要传送约 270 MB，约等于 36 Mbps，相当于一条家用宽带。
- 对 Cloudflare 的网络来说，这就像高速公路上同时多了几辆自行车。
- 即使 10 万人在同一分钟打开（约 3.6 Gbps），也只占它全网带宽的百万分之七左右。

Cloudflare 免费版真正的上限都与访问人数无关：

- 每月最多 500 次构建；
- 每个站点最多 20000 个文件，本站只有十几个；
- 单个文件最大 25 MiB，最大的 `app.js` 不到 1 MB。

### 用户端：每口锅能炒多大的菜

用与线上相同的构建产物（同一份 `app.js`），在 Chromium 浏览器里实测。“慢 4 倍”用浏览器开发者工具模拟低配笔记本或手机。

| 文件 | 大小 | 识别（普通电脑 / 慢 4 倍） | 生成（普通电脑 / 慢 4 倍） |
|---|---|---|---|
| 真实样例：中文决议草案（1–2 页） | 0.04 MB | 0.3 秒 / 0.6 秒 | 0.3 秒 / 0.8 秒 |
| 100 条行动条款（约 400 段） | 0.04 MB | 0.3 秒 / 0.9 秒 | 0.5 秒 / 2.0 秒 |
| 500 条行动条款（约 2000 段） | 0.04 MB | 0.5 秒 / 2.2 秒 | 1.3 秒 / 5.3 秒 |
| 1000 条行动条款（约 4000 段，远超任何真实文件） | 0.05 MB | 1.0 秒 / 3.3 秒 | 2.5 秒 / 9.8 秒 |
| 带 13 张大图，接近 20 MB 上限 | 18.3 MB | 0.5 秒 / 1.2 秒 | 1.8 秒 / 6.6 秒 |

- 22 次测试全部成功生成，没有一次报错或崩溃。
- 最大的测试中，网页脚本内存峰值约 70 MB，普通电脑和近几年的手机都能承受。
- 真实的模联文件通常只有几十段，在任何设备上都是“一眨眼”。
- 只有异常大的文件，才会在低配设备上让页面停顿几秒到十秒：处理是在浏览器主线程同步完成的，期间页面不响应点击，但不会出错。
- 超过 20 MB 的文件在上传时就会被拒绝，并给出提示。

## 稳定性

### 天生稳定的地方

- **没有可以宕机的后端**：没有服务器程序、数据库、账号系统，只有 Cloudflare 上的几个静态文件。
- **用户之间互不影响**：每个人在自己的浏览器里处理，一个人的怪文件不会拖慢别人。
- **发布不会把网站弄坏**：
  - Cloudflare Pages 的每次发布都是原子切换，新版本完整上线后才替换旧版本；
  - 构建失败时，网站继续提供上一个版本；
  - 后台可以一键回滚到任何历史版本。
- **出错就不给文件**：任何一项安全校验不通过，页面会说明原因，而不是交出一个可能改坏内容的文件。
- **旧浏览器有提示**：太旧的浏览器（例如 IE）会看到“该装哪个浏览器”的说明，而不是白屏。

### 需要留意的风险

| 风险 | 可能性 | 影响 | 应对 |
|---|---|---|---|
| 国内部分运营商访问 `pages.dev` 慢或打不开 | **中**，因地区和运营商而异 | 打不开网页（已打开的页面不受影响） | 会前分发桌面安装包；需要时绑定自有域名并在国内实测 |
| Cloudflare 平台故障 | 低，偶有全球性事故 | 网页暂时打不开 | 桌面版完全离线，不受影响 |
| 低配设备处理特大文件 | 低（真实文件很小） | 页面停顿几秒 | 耐心等待，或换电脑处理 |
| 免费计划没有服务等级承诺（SLA） | — | 出事时没有赔偿 | 对重要会议，以桌面版作为备份 |

- **跨境访问**是最大的不确定因素。
  - 2026-10-05 在维护者本机上做过一次不经代理的直连检查：首页、脚本、样式和版本摘要都正常返回，且与发布构建逐字节一致；
  - 但这只代表当时那条线路。也有用户报告，Cloudflare 托管的网站在国内首次加载要好几秒（[示例](https://juejin.cn/post/7438822895227256832)）。
  - 好在网页只有 0.27 MB，而且打开之后处理文件完全不再联网，所以“能打开”之后就不会再受网络影响。

## 给会议组织者的建议

1. **会前**：把 DMG / EXE 和[安装教程](https://github.com/lsyl71271-lgtm/munword-formatter/releases/latest/download/PKUNMUN2026-Install-Guide.txt)发给代表，桌面版断网也能用。
2. **会中**：网页版当作“随开随用”的入口；遇到打不开，直接换桌面版或磁盘映像里的「直接用浏览器打开.html」。
3. **可选优化**：
   - 绑定一个自有域名，并在主要运营商上实测打开速度；
   - 给带版本号的 `app.js` / `styles.css` 设置长期缓存，让第二次打开连“确认更新”的往返都省掉。

## 测量方法与局限

- 测量环境：一台云端 Linux 容器里的无界面 Chromium，运行与网站相同的网页程序（`pnpm build:static` 的产物，桌面版用的也是它）。
  - 测试文件是用脚本生成的合成决议草案，加上仓库里的验收样例。
  - 每个时间从点击按钮算起，到第 03 步出现或下载开始为止。
- 本次无法从测量环境直接访问线上网站（该环境的网络策略不允许连接 `pages.dev`），所以：
  - 没有测量线上的真实网络延迟；
  - 也没有做压力测试。对公共网站做压力测试既没必要（压的是 Cloudflare 而不是本程序），也可能触发平台的防护机制。
- Cloudflare 的限制以[官方文档](https://developers.cloudflare.com/pages/platform/limits/)为准，可能随时间调整。
