# v2.0.0 — 八种文书；安卓传入文件不再被旧文件覆盖；只从 main 发布、版本不可覆盖；网页版旧浏览器提示

2.0.0 包含 1.9.0 的全部内容（外交协定、联合声明，决议草案沿用原文件名，见 [release-1.9.0.md](release-1.9.0.md)），并根据 Codex 的核查意见（2026-10-10）修复下面几处。排版规则、第 03 步人工修改入口、两套引擎的内容校验都不变。

## 安卓：传入的文件以最后一个为准

- **问题**（Codex 复现）：页面的文件输入框还没出现时传入文件 A，A 的交付会每 100 ms 重试；输入框出现后又传入 B，B 立即交付，但 A 留下的重试晚一步执行，把页面上的文件换回了 A。点选文书类型后的“重新放回”也有同样的问题。这个问题在 1.8.5.2 和 1.9.0 里都存在。
- **修复**：
  - `android/bridge.js`：每传入一个文件、用户每亲手选一个文件，代次加一，并清掉等待中的定时器；还在等待的交付和重新放回只属于开始时的代次，代次一过就停。重新载入页面时一切从头开始。
  - 原生侧（`MainActivity.java`）：每次「打开方式 / 分享」按顺序编号，读得慢的旧文件读完时已不是最新就丢弃（出错也不再提示）；页面分块读回时始终读同一个文件，读的过程中到达的新文件留到下一次交付，不会把两份文件拼在一起；Activity 销毁后不再弹窗、不再调用页面。
- **测试**：`tests/android.test.mjs` 按 Codex 的探针顺序回放（输入框出现前传入 A → 输入框出现 → 传入 B → 等 A 的重试），旧代码得到 B→A，新代码只有 B；另测类型切换后的重新放回。原生侧的顺序与读回规则有静态检查，并由 CI 的十六个安卓模拟器跑全部流程（快速连续传入两个文件的情形没有在真机上单独复现）。

## 发布：只从 main 发布，已发布的版本不可覆盖

- **以前**：开发分支的推送和任意手动触发都会更新正式的 Latest；发布不等完整的源码检查；同一版本号重建时会覆盖附件，或删掉 tag 再建。
- **现在**：
  - 只有 `main` 的推送（或在 `main` 上手动触发）才发布；开发分支跑完全部检查但不发布，构建产物就是测试版。
  - 发布前必须通过同一提交的完整源码检查：`source-checks.yml` 变成可复用工作流，由 `offline-installers` 在同一次运行里调用，`release` 依赖它。
  - tag 改为 `v<版本>`（只更新安卓时为 `v<版本>.<修订号>`）。已发布的版本从不修改：同一 tag、文件相同就什么都不做；文件不同直接报错，必须升版本号。不再覆盖附件、删除或移动 tag。
  - 每个版本附 `release-manifest.json`：引擎版本、各客户端修订号、安装包字节来自的提交（sourceCommit）、本次验收的提交（validationCommit）、构建编号、每个文件的 sha256 与大小、安卓签名证书指纹。
  - `tests/desktop.test.mjs` 检查这些规则（只有 main、依赖源码检查、没有覆盖或删除 tag 的命令）。

## 网页版：旧浏览器和程序文件加载失败时有说明

- **以前**：网页版（以及 Python 本机页面）直接加载 `app.js`，浏览器太旧或 `app.js` 没加载成功时是白屏；桌面版和安卓版早已有检查。
- **现在**：网页版用和桌面版同一份兼容检查（`local_web/compat-loader.mjs`），各用自己的措辞：
  - 浏览器太旧（低于 Chrome/Edge 99、Safari 15.4、Firefox 104）时说明该装哪个浏览器；
  - `app.js` 加载失败时提示刷新或改用离线安装包。
  - 网页不加桌面版 `file://` 的那套安全策略。
- **测试**：jsdom 中旧浏览器、新浏览器、`app.js` 加载失败三种情况；本地用真实浏览器访问网页版构建：Chromium 98 显示说明，99、109、141 正常进入（8 张类型卡片），去掉 `app.js` 时显示加载失败说明。
