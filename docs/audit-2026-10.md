# 2026-10 独立审查后的修复（基于 v1.7.1）

审查报告与可复现样本不在仓库内（合成 DOCX，无真实文件）。本轮只做报告第一阶段的小步修复，学标参数、界面流程和第 03 步人工修改入口不变；自动回归不填写第 03 步。

## 内容安全

- 隐藏（vanish/webHidden/specVanish）与删除线（strike/dstrike）文字在任何改写中保持原样：含这类文字的段落不再“扁平化”重建；国家名单、签字行、第 03 步带标签字段遇到它们时保留原样并提示（第 03 步修改则中止并说明原因）。
- 两个引擎的内容守卫新增独立检查：格式化前隐藏或带删除线的字符，必须按原顺序仍隐藏/仍带删除线，否则中止输出。此前守卫不比对 run 属性，校验结果会误报“已保留”。
- 句末标点：句末文字为隐藏或删除线时不自动改标点并提示；句末是 REF 域结果或超链接时，标点写在域/链接之后，不再写进会被 Word 更新掉的域结果。
- 条款末尾带分页符或手动换行时，句末标点此前不改，并误报“改写会改变该段中的链接、域、书签或修订结构”；Python 遇到手动换行会把新标点写到换行之后（下一行）。现在两引擎都把标点写在换行/分页符之前并保留原符号；浏览器重建段落时把换行写成 `w:br`，不再写进文字。

## 识别与两引擎一致性

- 语言判定写入共享策略 `language`，两引擎同一规则：英文文件中引用少量汉字不再被当成中文（浏览器曾把标题改成“决议草案”、标点改为全角）。
- 浏览器的名单结束判定与 Python 一致：主体句（如 “The Assembly of States Parties,”）、条款动词、PART 标题结束名单，不再并入附议国。
- Python 把 Word 自动编号的 0 级段落也作为行动性条款起点，以“呼吁/支持/希望”等两表共有动词开头的行动条款不再被当成序言。
- 以冒号结尾的自动编号条款之后，同一列表同级的条款不再被降为下一级。
- 页首无标签字段只在正文开始（共享 `headerBoundary`）之前识别：“一、问题背景”等编号小标题不再被当成代表；Python 页首修复按文件语言写标签，英文立场文件不再写入中文标签。
- Python 拆分内嵌子条款时不再切开超链接或修订包装（此前会被自身修复校验拒绝、整份文件 409），改为保留并提示，与浏览器一致。

## 内嵌子条款拆分（两引擎同一规则）

- 规则写入共享策略 `embeddedSubclause`，工作文件、指令草案、决议草案都适用（此前 Python 只处理决议草案）。冒号或分号后紧跟的“（一）（子）（甲）”等标记，所在段落是条款（第X条、阿拉伯数字编号、括号标记、行动动词开头或原生编号）时拆开：第X条原段落中的一级标记在同一段内换行，其余标记另起一段，新段落不继承原段落的编号和缩进。
- 此前同一份纯文本决议两引擎段落边界不同：浏览器不拆分号后的标记，Python 把深层条款之后的“（二）”用换行挂在深层段落里。现在两者一致，例如“第一条 …：（一）…：（子）…；（丑）…；（二）…”拆为“第一条 …：↵（一）…：”“（子）…；”“（丑）…；”“（二）…”。
- 标记前有制表符或手动换行时视为作者有意排版，不拆（原规则不变）。不在条款中、段落含域或内容控件、拆分点位于超链接或修订内时不拆，两引擎都提示原因。
- 浏览器拆分时可以绕开整段位于一侧的链接、书签和修订，不再因段内任何链接而整段放弃。
- 拆分的段落带分节符时，分节符移到最后一段，不再复制到每一段（复制会多出分节）。

## 样式继承

格式化会重置段落样式与字符样式，因此两引擎先把样式的效果写到段落和文字上。以下情况此前写错，均用合成文件复现：

- 默认段落样式 ID 不是 “Normal”（中文 Word 为 “a”）时不被读取：整篇隐藏的损坏不会被清除，输出在 LibreOffice 中为空白页。
- 文本框中的文字继承了外层段落的样式（例如变为加粗、下划线）。
- 通过 `abstractNum/lvl/pStyle` 链接到段落样式的列表级别（ECMA-376 §17.9.23）被写成 0 级，子项在样式被重置后变为顶层编号。
- 清除整篇隐藏/删除线损坏时会删掉所有样式中的这两种属性，只在脚注或页眉中使用的隐藏样式也被公开。现在只清除文档默认值和正文能用到的样式。
- 浏览器沿 basedOn 链读取加粗、斜体、下划线时越过了默认样式：损坏的加粗 Normal 会通过任何基于它的样式让正文变粗。现在与 Python 一样在默认样式处停止。

## 第 03 步

- Python 立场文件带标签的页首字段，第 03 步修改不再被 409 拒绝。
- 浏览器修改字段时只改页首段落，不再改写正文中与旧值相同的段落。
- 网页国家输入框保存原始文字，逐字输入的分隔符和空格不再被吞掉。

## 包、预览与本机服务

- 大写扩展名（如 `header1.XML`）的部件同样做 DTD/实体检查；浏览器支持 UTF-16 编码的 XML 部件。
- 预览副本删除所有找不到图片来源的引用，避免宿主页面请求 `/null`。
- 本机引擎拒绝来自非本机页面且不在白名单中的浏览器 POST（403，读取请求体之前）；XML 结构过深等解析错误归为文件问题（422）。
- XML 嵌套超过 256 层（libxml2 的上限）：浏览器此前递归到栈溢出、报“程序内部错误”。现在两引擎都报“XML 嵌套层级过深（超过 256 层）”的文件问题；浏览器在解析前对每个 XML 部件线性扫描（4 000 段决议约 3 ms）。
- 依赖：lxml 统一为 6.1.3；Python ≥3.10 使用 fastapi 0.142.2 / python-multipart 0.0.32（含已公开漏洞修复）；Python 3.9（macOS `/usr/bin/python3`）使用其仍支持的最新版本 fastapi 0.128.8 / python-multipart 0.0.20。

## 发布与安装

- `scripts/package-release.py` 从 Git 索引读取受控文件；工作区有未暂存改动时拒绝打包，避免本地替换的文件进入发布包。
- Windows 启动器比较服务版本：旧版引擎占用端口时先尝试停止，无法停止则提示；安装时旧引擎停不下来即中止，不再“安装成功”却继续使用旧引擎。
- macOS：应用版本号此前停在 1.2，现在与 `VERSION` 一致并有测试约束；端口 8000 被占用时 launchd 每 5 秒重启一次并写入一段错误日志，现在改为每 60 秒（打开应用仍会立即重启服务），日志超过 5 MB 时保留一份旧日志，与 Windows 相同。只做了 bash 语法检查和 Linux 上的模拟，未在真实 Mac 上运行。

## 性能与开发脚本

- 浏览器生成时只解析一次文件（此前解析三次、重新压缩一次）；输出逐字节不变，Chromium 中 4 000 段决议生成时间约少 10–15%。
- 内容守卫查找内容控件时不再遍历全部元素：jsdom 测试环境中 990 段决议从 60 秒降到 2.2 秒（浏览器本来就是线性）。
- `scripts/docx_compare.py` 使用与引擎相同的安全解析设置（不展开实体、不访问网络）。
- 共享策略中引用的 `docs/v1.6.3-merge-report.md` 从未进入仓库，改为说明测量记录未保存并指向发布摘要。

## 第三轮（v1.7.2）

- 中文词头：序言新增“深切关切、深表关切、进一步回顾”，行动新增“促请、进一步呼吁”（共享策略，两引擎）。“进一步回顾”原已在行动词表中，与“回顾”一样两表共有，按条款位置判定：序言中加下划线，条文中为斜体。
- 浏览器隐藏/删除线守卫按 UTF-16 单元与码点混合比较，含表情符号或扩展汉字的隐藏、删除线文字未改动也会被判为“变为可见”并中止下载；现统一按码点比较（Python 原本正确）。
- 自动改写（标题用词、标签、编号标记、句末标点）统一在改写前后比对该段的隐藏/删除线文字：会删除带标记字符或去掉标记时，只回退这一段并提示“改写会删除隐藏或删除线文字或去掉其标记，已保留原样”，最终守卫不放松。此前例如“非友好修[隐藏]正案1.3.2”的标题被规范为“修正案…”时会删掉隐藏文字，整份输出被拒绝。委员会/议题标签（含只有中间片段隐藏、带删除线空白）另有提前检查，提示“未按范例删除标签”；只有值隐藏时仍删除标签。第 03 步人工修改含隐藏或删除线文字的标题仍按原规则拒绝。Python 结构修复在无法就地编辑时不再重建带标记的段落。
- 拆分内嵌子条款时，标记前带删除线或隐藏的空白此前会被当作分隔空白删除，且发生在守卫快照之前；现保留。
- 已确认无问题的路径：整篇统一损坏被清除时，脚注和页眉中的隐藏/删除线保留；文本框中的隐藏文字；整段隐藏的原生编号条款保留编号；整篇隐藏文件中的子条款拆分。拆分点恰为隐藏标记时仍会拆分（内容和标记均保留），未改。
- 版本号统一为 1.7.2（VERSION、package.json、两种页面页脚、macOS Info.plist、README），并有测试约束。

## 仍未处理

- 第X条段落内用手动换行开始的一级分款，在两端对齐时 Word 会拉伸换行前的一行。Word 的兼容选项 `doNotExpandShiftReturn` 可以避免，但无法在本环境验证 Word 的表现，且需按 OOXML 规定的元素顺序写入 settings.xml，未加入。
- 切换属性（加粗、斜体等）在段落样式与字符样式同时设置时 Word 按异或处理，引擎按就近取值，可能把本不加粗的文字变粗；未证实，需要 Word 实机确认。
- 浏览器排版仍在主线程同步执行（4 000 段决议生成约 2.4–2.7 秒无响应）；根本解决需要移入 Web Worker。
- 浏览器对表格和文本框中的段落也会补写样式编号，Python 只处理正文段落；未发现由此产生的输出差异，未改。
- 首行不符合标题格式时（如“决议草案（修订稿）”），Python 仍把它当作标题（左对齐），浏览器不当作标题（两端对齐）。v1.7.1 已如此，与隐藏文字无关，本轮未改。
