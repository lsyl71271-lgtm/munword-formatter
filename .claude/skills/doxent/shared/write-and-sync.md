# 写操作与同步规则

## 真实写操作

以下动作会修改真实 Doxent 数据：
- create
- update
- delete
- move
- rename
- complete
- uncomplete
- 会创建或落真实记录的 upload

## 确认规则

在执行高风险动作前，必须确认：
- 对象标识
- 对象名称
- 对象类型
- 影响范围

这条规则适用于 delete、move、rename、complete、uncomplete 以及类似的直接状态变更动作。

## 同步规则

- 首次全量未完成但处于 `partial_idle` 时，允许 `doxent_api.py` 的 `PARTIAL_WRITE_PATHS` 中的 POST 写操作；新增业务写接口只需维护该精确路径白名单。批次运行中仍须等待，写请求本身不发送部分读取的补批通知。
- 此阶段写入基于本地已有数据，不能把查询未命中当作云端不存在，也不能把本地递归操作结果当作覆盖了尚未同步的全部对象；放行不会消除原有并发同步风险。
- 同一轮用户请求中，只要实际发起过增删改、移动、重命名、任务状态变更或上传等写接口，就在整轮操作及必要的结果检查结束后、最终回复前，通过 `doxent_api.py` 统一调用一次 `POST /open-model/sync`。不要每个写接口后都调用，也不要因涉及多个模块而重复调用；“每轮一次”由 Agent 根据本轮执行记录保证，不新增收尾命令。
- `/open-model/sync` 已纳入 POST 白名单，首次全量未完成但处于 `partial_idle` 时也可调用；同步运行中仍由脚本按原规则等待，状态异常或超时则停止。本轮已经发起过该同步请求时，不再重复补调。
- 纯读取操作或所有写请求都在发送前被门禁拦截时，不自动补同步。已经实际发起过写请求时，即使其中部分失败，也在本轮结束前补调一次。
- 补同步失败或结果不明时，单独说明同步情况，保留已成功的写入结果，不重放已成功或结果不明的增删改，也不为收尾反复调用同步接口。
- 对用户说明结果时，要明确 sync 只表示“已触发同步流程”，不代表远端已经完成最终可见。
